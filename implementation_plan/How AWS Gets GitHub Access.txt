================================================================================
            HOW AWS GETS ACCESS TO GITHUB
            AWS CodeStar Connection - OAuth Authorization Flow
================================================================================


SIMPLE ANSWER
-------------
AWS does NOT use a username/password or a PAT (Personal Access Token) to access
GitHub. Instead, it uses OAuth 2.0 — which means GitHub grants AWS permission
through a secure browser-based approval flow, similar to "Login with Google".


================================================================================
PART 1 — WHAT HAPPENS WHEN TERRAFORM CREATES THE CONNECTION
================================================================================

When you run:

    terraform apply

Terraform creates this resource:

    resource "aws_codeconnections_connection" "github" {
      name          = "lawyered-github-repository"
      provider_type = "GitHub"
    }

At this point:
  - AWS creates a connection record in its system
  - Status = PENDING
  - AWS does NOT yet have access to GitHub
  - No webhook, no token, nothing is set up yet
  - The connection is basically an empty slot waiting to be authorized


================================================================================
PART 2 — THE ONE-TIME MANUAL APPROVAL (How AWS actually gets access)
================================================================================

After terraform apply, someone (you) had to do this manually:

  STEP 1:
    Go to AWS Console
    --> Developer Tools
    --> Settings
    --> Connections
    --> Find "lawyered-github-repository"
    --> Click "Update pending connection"

  STEP 2:
    A popup appears: "Connect to GitHub"
    You click "Connect to GitHub"

  STEP 3:
    Your browser redirects to github.com
    GitHub shows: "AWS Connector for GitHub wants permission to access:
                   - Read repository contents
                   - Read metadata
                   - Webhooks (read and write)
                   - etc."
    You click "Authorize AWS Connector for GitHub"

  STEP 4:
    GitHub redirects back to AWS Console
    AWS Console shows: Connection status = AVAILABLE

  WHAT HAPPENED BEHIND THE SCENES:
    - GitHub issued an OAuth token to AWS
    - AWS stored this token securely in its internal systems
    - AWS also installed a webhook on the GitHub organization automatically
    - The webhook URL looks like:
        https://webhooks.codeconnections.us-east-1.amazonaws.com/...
    - From now on, every push to any Lawyered-in repo notifies AWS automatically


================================================================================
PART 3 — WHAT AWS STORES AND WHAT YOU NEVER SEE
================================================================================

After authorization:
  - AWS stores the OAuth token internally (you cannot see it, it is encrypted)
  - You only see the Connection ARN:
      arn:aws:codeconnections:ap-south-1:344367180480:connection/57bb41a6-94e5-4be9-9364-73bc9da899d3
  - This ARN is what your Terraform uses everywhere
  - The actual GitHub token is hidden inside AWS and rotated automatically

You never need to:
  - Create a GitHub PAT for pipeline triggers
  - Store any GitHub secret in AWS Secrets Manager for pipeline triggers
  - Renew or rotate anything manually

NOTE:
  This is DIFFERENT from the GitHub PAT we are planning to add for the
  manifest update feature. That PAT is for CodeBuild to PUSH to k8s-manifest
  repo (write access). The CodeStar Connection only gives AWS READ access
  to pull source code.


================================================================================
PART 4 — HOW THE WEBHOOK WORKS (Push to GitHub triggers AWS)
================================================================================

After the connection is AVAILABLE, this is what happens on every git push:

  Developer's machine
      |
      | git push origin staging
      |
      v
  GitHub.com (Lawyered-in/lawyered-in-website)
      |
      | GitHub fires webhook to AWS (installed during OAuth approval)
      | Webhook payload contains: repo name, branch name, commit SHA
      |
      v
  AWS CodeStar Connection (lawyered-github-repository)
      |
      | AWS verifies: is this connection AVAILABLE?
      | AWS checks: which pipeline is watching this repo + branch?
      |
      v
  AWS CodePipeline (lawyered-in-website)
      |
      | Source stage wakes up
      | Downloads source code ZIP from GitHub using the stored OAuth token
      | Stores ZIP in S3
      |
      v
  AWS CodeBuild (lawyered-in-website-build)
      |
      | Extracts ZIP, runs buildspec
      | Builds Docker image, pushes to ECR


================================================================================
PART 5 — HOW AWS IS AUTHORIZED TO USE THE CONNECTION (IAM)
================================================================================

Just having the connection is not enough. The CodePipeline role also needs
explicit IAM permission to USE that connection.

In modules/codepipeline/main.tf:

    resource "aws_iam_role_policy" "pipeline" {
      policy = jsonencode({
        Statement = [
          {
            Action   = ["codestar-connections:UseConnection"]
            Effect   = "Allow"
            Resource = var.github_connection_arn
          }
        ]
      })
    }

Without this:

  - The connection could be AVAILABLE
  - But CodePipeline would get "Access Denied" when trying to pull from GitHub
  - The IAM policy is the second layer of security

So there are TWO things required:
  1. Connection must be AVAILABLE (OAuth approved by a human)
  2. IAM role must have codestar-connections:UseConnection permission


================================================================================
PART 6 — ONE CONNECTION vs MULTIPLE CONNECTIONS
================================================================================

Why do we use ONE connection for all 7 repos?

  - The OAuth approval is at the GitHub ORGANIZATION level (Lawyered-in)
  - Once approved, AWS can access ALL repos under Lawyered-in organization
  - No need to create a separate connection per repo
  - All 7 pipelines pass the same connection ARN:
      aws_codeconnections_connection.github.arn

If you had repos from a DIFFERENT GitHub organization (e.g., a vendor):
  - You would need a separate connection for that org
  - And that org admin would need to approve the OAuth request


================================================================================
PART 7 — DIFFERENCE BETWEEN CODESTAR CONNECTION AND GITHUB PAT
================================================================================

  Feature                  | CodeStar Connection           | GitHub PAT (Personal Access Token)
  -------------------------|-------------------------------|------------------------------------
  Purpose                  | Pull source code (read)       | Push to repos (write)
  How AWS stores it        | Encrypted internally by AWS   | You store it in Secrets Manager
  Renewal needed           | No (AWS manages it)           | Yes (expires, you rotate manually)
  Set up by                | OAuth browser approval        | You create it on github.com/settings
  Used in Terraform for    | CodePipeline Source stage     | Not used in pipelines currently
  Used for manifest update | No                            | YES (planned feature)
  Visible to you           | Only the connection ARN       | Full token string (sensitive)

In our planned manifest update feature:
  - CodeBuild needs to WRITE to Lawyered-in/k8s-manifest
  - CodeStar Connection cannot do this (read-only for pipelines)
  - So we need a GitHub PAT stored in AWS Secrets Manager
  - Secret name: lawyered/github/token


================================================================================
PART 8 — SUMMARY IN PLAIN WORDS
================================================================================

  1. Terraform creates a connection slot in AWS (status: PENDING)

  2. You go to AWS Console and click "Authorize" -- this opens GitHub OAuth
     GitHub asks: "Allow AWS to access your repos?" -- you click YES

  3. GitHub gives AWS a hidden token and installs a webhook

  4. From now on, every push to staging branch on any Lawyered-in repo
     fires that webhook, AWS wakes up the right pipeline

  5. The pipeline uses the hidden token to download your source code

  6. CodeBuild builds the Docker image and pushes to ECR

  7. All of this happens automatically after that one-time approval
